# Profiling

The Cicero VM provides several profiling modes that can be enabled independently to collect compile-time and runtime stats. Depending on the profiler, the profiling results are written to `stdout` in csv format.

## How to profile?
1. Modify `Options.v3` and set the profiling mode you want enabled as `true`.
2. Run `make` to build cicero.
3. Run the `.co` files you want to profile in `tier=1`. For example, `bin/cicero.x86-64-linux -tier=1 -suppress-output=true path/to/file1.co path/to/file2.co`

> [!TIP]
> If you are profiling a compile-time statistic, make sure to run cicero with `-do-not-evaluate=true`.

## All profiling options
### Static Bytecode Counts

Counts the number of occurrences of every opcode generated during compile time.

#### CSV Output

| Column | Description |
|---------|-------------|
| `instruction` | Opcode name |
| `counts` | Number of times the opcode appears in the generated bytecode |

---

### Dynamic Bytecode Profiling

Profiles opcode execution during runtime. For every opcode, it records how often it executes and the total time spent executing that opcode.

#### CSV Output

| Column | Description |
|---------|-------------|
| `instruction` | Opcode name |
| `counts` | Number of runtime executions |
| `total execution time (μs)` | Total execution time accumulated for the opcode |

---

### Static Opcode Pair Counts

Records opcode pairs that occur consecutively during bytecode generation (compile time).

> [!NOTE]
> Opcode pairs are tracked independently for each bytecode object. Pair boundaries do **not** span across different bytecode objects.

#### CSV Output

| Column | Description |
|---------|-------------|
| `opcode` | Current opcode |
| `next opcode` | Following opcode |
| `counts` | Number of occurrences during compilation |

---

### Dynamic Opcode Pair Counts

Profiles opcode pairs that execute consecutively at runtime and records their dispatch costs. The dispatch cost measures the elapsed time between the completion of the first opcode and the start of execution of the following opcode.

Unlike static opcode pair profiling, dynamic opcode pair profiling is not isolated to individual bytecode objects. Instead, they are tracked across bytecode object boundaries. Per-bytecode object statistics can still be derived by identifying frame transitions through `RETURN -> XXX` and `RETURN_INIT -> XXX` opcode pairs.

#### CSV Output

| Column | Description |
|---------|-------------|
| `opcode` | Current opcode |
| `next opcode` | Following opcode |
| `counts` | Number of runtime occurrences |
| `total dispatch cost (μs)` | Total dispatch time accumulated for the opcode pair |

---

### Jump Outcome Profiling

Profiles the runtime behavior of jump instructions by recording whether each conditional jump is taken or not taken.

Stats are maintained separately for every jump instruction in every bytecode object.

#### CSV Output

| Column | Description |
|---------|-------------|
| `Line Number` | Source line containing the instruction |
| `Bytecode ID` | Bytecode object identifier |
| `Instruction Index` | Instruction position within the bytecode |
| `Function Identifier` | Static function identifier id|
| `Function Label` | Function or method name |
| `Instruction` | Jump opcode |
| `Jumps taken` | Number of times the jump was taken |
| `Jumps not taken` | Number of times the jump was not taken |

---

### Inline Cache Profiling

Profiles inline cache performance for instructions that utilize inline caches (currently `LOAD_FIELD` and `STORE_FIELD`).

For each inline cache site, the profiler records cache hits, misses, and the number of distinct receiver classes observed.

#### CSV Output

| Column | Description |
|---------|-------------|
| `Line Number` | Source line containing the instruction |
| `Bytecode ID` | Bytecode object identifier |
| `Instruction Index` | Instruction position within the bytecode |
| `Function Identifier` | Static function identifier |
| `Function Label` | Function or method name |
| `Instruction` | Cached opcode |
| `Hits` | Number of inline cache hits |
| `Misses` | Number of inline cache misses |
| `Classes seen` | Number of distinct receiver classes observed |

---

### Function Profiling

Profiles calls based on the **static** definition of the function/method.

The profiler relies on `FunctionProfileMetadata`(see `src/object/Function.v3`) to idenfity the "same"(functions with the same identifier id) function/methods.

> [!NOTE]
> All instances of a closure created from the same function definition share the same identifier id.
> Likewise, method calls are aggregated by the underlying method definition,
> so x.show() and y.show() contribute to the same identifier if they resolve to the same method implementation.

#### CSV Output

| Column | Description |
|---------|-------------|
| `Function identifier` | Static function identifier |
| `Function label` | Function or method name |
| `calls` | Number of invocations |
| `inclusive execution time (μs)` | Total time including child calls |
| `exclusive execution time (μs)` | Time excluding child calls |

---

### Caller–Callee Profiling

Profiles relationships between callers and callees using static function identifiers.

Like function profiling, identical static function definitions are grouped together regardless of individual closure instances or object instances.

#### CSV Output

| Column | Description |
|---------|-------------|
| `caller identifier id` | Static identifier of the caller |
| `caller label` | Caller function name |
| `callee identifier id` | Static identifier of the callee |
| `callee label` | Callee function name |
| `calls` | Number of invocations |
| `execution time (μs)` | Total execution time spent in the callee |

---

### Compilation Time Profiling

Measures compilation time for every bytecode object produced by the compiler.

In most cases, a function or method corresponds to a single bytecode object. The exception is top-level (`repl`) code, which will consist of multiple bytecode objects compiled independently.

#### CSV Output

| Column | Description |
|---------|-------------|
| `Bytecode ID` | Bytecode object identifier |
| `Label` | Function, method, or bytecode label |
| `Inclusive Compilation Time (μs)` | Average compilation time |
